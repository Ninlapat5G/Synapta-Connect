ผู้ตรวจ: Security & QA · วันที่: 2026-11-20
ตรวจกับ: `D:\claude_code\exe\SynaptaConnect-v0.2.1.exe` (build 03:10) โดยรันจริงบนพอร์ตปกติ (52400–52402) ใช้ data-dir ชั่วคราว

**สมมติฐาน:** เครื่องส่วนตัว ใช้บน LAN หรือ Tailscale และผู้โจมตีอยู่ในวง LAN เดียวกัน

## สิ่งที่ยังเปิดอยู่

### ต้องแก้ หรือเขียนเป็นเงื่อนไขการใช้งาน

**1. ใครก็ได้บน LAN ปิดการใช้งาน agent ได้ ด้วยการเปิด connection ค้างไว้ 256 อัน** (`tls.rs:28-30, 183-200`)
- **ส่วนนี้ทำอะไร:** จำกัด connection พร้อมกันไว้ที่ 256 และให้เวลา TLS handshake 10 วินาที
- **ปัญหา:** handshake ไม่ต้องใช้ใบรับรอง (เปิดไว้ให้จับคู่) และหลัง handshake แล้ว connection ที่ไม่ส่งอะไรเลยจะค้างไปตลอด ไม่มี idle timeout
  **ทดสอบแล้วกับ v0.2.1:** เปิด TLS connection เปล่า 256 อัน → connection ใหม่ทุกอันถูกตัดทันที **รวมถึงเครื่องที่จับคู่แล้วด้วย** ผ่านไป 35 วินาทีก็ยังเป็นแบบนั้น
- **แก้ (เล็ก):** connection ที่ไม่มีใบรับรองต้องส่ง request แรกภายในไม่กี่วินาที และปิดเมื่อตอบเสร็จ เพราะใช้แค่ `hello` กับการจับคู่
  และจำกัดจำนวน connection ที่ไม่มีใบรับรองไว้ต่างหาก (เช่น 16) ไม่ให้แย่ง slot ของเครื่องที่จับคู่แล้ว ไม่ต้องเพิ่ม dependency
- **ถ้าข้าม:** เข้าเครื่องไม่ได้ แต่คนในวง Wi-Fi หรือ VPN เดียวกันทำให้ Synapta Code ใช้เครื่องนั้นไม่ได้ ด้วยสคริปต์ไม่กี่บรรทัด
- ส่งให้หลังบ้านแล้ว (ยังไม่ได้รับคำตอบ)

### ควรแก้

**2. คนแปลกหน้าทำให้เจ้าของจับคู่ไม่ได้** (`pairing.rs:132-139, 174-177`)
(ก) เดาผิด 5 ครั้งทำลาย OTP — ตั้งใจไว้ ถูกต้อง แต่คนบน LAN ยิงซ้ำได้ทุกครั้งที่เจ้าของเปิด
(ข) handshake ค้างได้สูงสุด 8 อัน และเมื่อเต็ม ตัวที่เก่าที่สุดจะถูกทิ้ง → การยิง step 1 รัว ๆ จะดันการจับคู่ของเจ้าของทิ้งก่อนที่จะถึงขั้น 2
แก้ที่ถูกที่สุด: ให้หน้าจัดการแสดงว่า "มีการเดาผิด X ครั้งจาก IP Y" เพื่อให้เจ้าของรู้ว่าทำไมจับคู่ไม่ได้

**3. อุปกรณ์ที่จับคู่แล้ว revoke อุปกรณ์อื่นได้** (`api.rs:73-77`) — ถ้า key ของ client รั่ว คนร้ายไล่เจ้าของออกได้ (แต่เพิ่ม key ใหม่ไม่ได้ เพราะถอด `otp.regenerate` ออกแล้ว)
แก้: ให้ `session.revoke` ผ่าน RPC revoke ได้แค่ตัวเอง ส่วนการ revoke อุปกรณ์อื่นทำจากหน้าจัดการบนเครื่องเท่านั้น

**4. ไม่มี audit log ถาวร** — หลัง agent รีสตาร์ต จะสืบย้อนหลังไม่ได้ว่าอุปกรณ์ไหนสั่งอะไร

### เล็กน้อย / ข้อสังเกต

**A. bind `0.0.0.0` รวม Radmin VPN** — บนเครื่องที่ทดสอบ agent ฟังบน Radmin VPN (`26.x.x.x`) ด้วย เครือข่าย Radmin มักมีคนแปลกหน้า และทำให้ข้อ 1 กับ 2 ยิงได้จากนอกบ้าน
**B. Job Object ผูกหลัง spawn** (`kill_tree.rs:5`) — ลูกที่ shell เปิดในไม่กี่มิลลิวินาทีแรกอาจหลุดจาก job หลังบ้านเขียนเป็น shortcut ไว้แล้ว ทดสอบจริงแล้วไม่เจอปัญหา รับได้สำหรับ Phase 0
ส่วน Unix (process group) ยังไม่ได้ทดสอบ
**C. ความปลอดภัยของการจับคู่ขึ้นกับ client:** client ต้อง (1) ใช้ host key ที่เห็นบน TLS จริงในการคำนวณ `client_confirm` (2) ตรวจ `host_confirm` (3) ปักหมุด key แล้วตัดทุกครั้งที่ไม่ตรง
ฝั่ง Synapta Code ต้องทำสามข้อนี้ ไม่งั้นการป้องกัน MITM ที่ agent ทำไว้ไม่มีผล — ต้องตรวจซ้ำตอนรวมระบบ
**D. ข้อจำกัดในการรวมระบบ:** ใบรับรอง Ed25519 ใช้กับ Windows Schannel (.NET `HttpClient`, `curl.exe` ของ Windows) และเบราว์เซอร์ไม่ได้
client ต้องเป็น Node.js, Rust หรือ Python/OpenSSL (Python ที่ผมใช้ทดสอบต่อได้)
**E. `--data-dir` ที่คนอื่นเข้าได้:** ถ้า `icacls` ล้มเหลว agent แค่เตือนใน log แล้วทำงานต่อ ค่าปริยาย (`%LOCALAPPDATA%`) ไม่มีปัญหานี้

## คำตัดสินสำหรับ v0.2.1: **ผ่านแบบมีเงื่อนไข (Conditional Pass)**

ทุกข้อจาก `SECURITY_REVIEW.md` ที่อยู่ในขอบเขต Phase 0 (SR-1 ถึง SR-7, 10, 14) และปัญหาที่พบใน v0.1.1/v0.2.0
(OTP อ่านได้จาก process อื่น, พารามิเตอร์ที่ไม่ได้เซ็น, process ลูกค้างตอน timeout) **ทำงานหรือแก้แล้วจริงตามที่ทดสอบจากภายนอก**
ไม่มีช่องให้คนบน LAN รันคำสั่งบนเครื่องได้ — ซึ่งเป็นความเสี่ยงหลักของระบบนี้

เงื่อนไขที่ต้องเขียนในเอกสารส่งมอบ:
1. ใช้บน LAN ที่ไว้ใจได้หรือ Tailscale เท่านั้น ไม่ใช้บน Wi-Fi สาธารณะหรือ Radmin VPN เพราะคนในวงเดียวกันปิดการใช้งาน agent ได้ (ข้อ 1)
2. รันในโหมด User (โหมด service ยังจับจอ/ส่ง input ไม่ได้)

ถ้าหลังบ้านแก้ข้อ 1 ทันก่อนส่ง เงื่อนไขข้อแรกจะเบาลงเหลือแค่ "ไม่แนะนำบนเครือข่ายสาธารณะ" — ต้องตรวจซ้ำเฉพาะ `tls.rs`
